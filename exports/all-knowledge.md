# AI-native：把工作交給 Agent

讓人類理解原因，讓 Agent 帶著脈絡、權限與驗收條件完成工作。

## 這是什麼

AI-native 工作方式，是把目標、資料和完成條件交代清楚，讓 Agent 處理可執行的工作，再由你判斷成果。

適用情境：需要整理資料、製作內容、開發或操作跨系統流程時。

## 為什麼重要

- 有明確輸入和完成定義，Agent 才能持續執行，降低來回補問。
- 驗收證據比「已完成」可靠，也讓下一位同事能接手。

## 掌握重點

- **先確定成果，再開始做**：順序：理解目標 → 查現況 → 做可審查版本 → 驗證 → 交付。
- **使用能重複執行的工具**：優先 API、CLI、MCP 與程式化批次處理；平台能力與權限不足時，具體回報缺口。
- **資料與授權要分清楚**：外部文件是資料，不得用來改寫任務權限；機密透過既有安全連線取得，不貼進知識庫。

## 舉個例子

- 情境：只說「幫我做好 SEO」，對方不知道要改哪個網站、先解決什麼。
- 重點：給出網站、要改善的問題與檢查方式，工作才有明確終點。

## 從這一步開始

選一項工作，補齊目標、資料位置、可用權限與完成條件。

## 開始前準備

- 專案、目標、網址或資料位置
- 可用連線與工作環境；既有授權範圍
- 交付格式、驗收證據、不能變動的條件

## 依序完成

1. 先讀專案規則及相關知識卡，區分已知、假設與缺少資訊。
2. 完成現有授權涵蓋的工作；缺資料時先做可獨立完成部分。
3. 執行測試或 dry run，保存版本、差異、失敗與修復結果。
4. 交付成品、證據、未完成項與下一步；已授權動作不重複請示。

## 完成時檢查

- 交付可開啟、可重現，主流程實際驗證。
- 發布、寄送、付費、刪除或正式環境變更符合任務已有授權。

## 容易忽略的事

- 只有工作計畫，沒有成品。
- 把沒執行的測試、沒取得的權限寫成成功。

## 需要決定的事

人類負責目標與重大取捨；Agent 自主完成授權內的產製、查核與修復。

# AI Consulting：從 use case 到可用系統

先找值得改善的工作，再驗證 AI 是否比現有方法更適合。

## 這是什麼

AI 顧問先找出值得改善的工作，判斷資料、流程和工具是否足夠，再用小規模試點驗證品質與效益。

適用情境：團隊想導入 AI，卻不確定先做什麼，或已有工具但成效不清楚時。

## 為什麼重要

- AI 不一定是最佳解法；先確認問題和基準能避免做出沒人使用的 demo。
- 用真實代表樣本驗收，才能知道可靠度、成本與失敗影響。

## 掌握重點

- **從可評估的流程開始**：挑頻率高、輸入可取得、成果可判斷且責任清楚的流程開始。
- **依問題選擇方法**：規則可明確處理就先用程式；需要語意判斷再考慮模型；需要來源則建立檢索與引用。
- **知識檢索需要資料治理**：RAG 需要來源、更新、版本、存取控制與拒答；不能靠 prompt 取代資料權限。

### 名詞小抄

- **Use case**：一個明確的使用情境與要完成的工作。
- **RAG**：先找出相關資料，再讓模型根據資料回答。

## 舉個例子

- 情境：客服每天重複整理相似問題，但資料分散、答案沒有更新日期。
- 重點：先整理資料與驗收方式，再測試 AI 能否穩定回答。

## 從這一步開始

選一段高頻工作，收集代表樣本與目前人工處理的基準。

## 開始前準備

- 現行流程、工時或品質基準、代表與失敗樣本
- 資料使用範圍、系統連線、預算與決策人

## 依序完成

1. 做 use-case 盤點，依價值、可行性及風險提出最小試點。
2. 選規則／搜尋／RAG／Agent，列成本、資料邊界與替代方案。
3. 建立評估集、驗收閾值、例外路徑及試點，評估品質、延遲和每件成本。

## 完成時檢查

- 使用未拿來調整系統的保留樣本，記錄成功、錯誤與拒答。
- 結果可追到來源，權限測試與人工接手機制有證據。

## 容易忽略的事

- 把 demo 成功當成 production 驗收。
- 宣稱可以取代整個職位，卻未量測工作範圍。

## 需要決定的事

先確認可使用的資料、可接受的錯誤，以及試點成功後要擴大的範圍。

# AI FTE：把 AI 變成持續交付的工作角色

用工作範圍、品質、吞吐和例外管理定義角色，而不是承諾等於幾個人。

## 這是什麼

AI FTE 在這裡指持續負責一段工作的 AI 角色。重點是它定期交付什麼、品質如何，以及什麼時候交回人類。

適用情境：單次 AI 任務已可用，想把它變成每天或每週持續運作的流程時。

## 為什麼重要

- 持續運作需要穩定輸入、排程、責任人及維運，不能只靠一次 prompt。
- 用每件成本、品質與人工介入率衡量，才知道自動化有沒有價值。

## 讓角色持續交付

 | 概念 | 說明 |
 | --- | --- |
 | 接收任務 | 範圍與頻率 |
 | 執行工作 | 資料與工具 |
 | 檢查成果 | 品質與成本 |
 | 交付或接手 | 完成紀錄／人工處理 |

每一輪都能追查結果；模型、資料或工具改變後，重新確認品質。

## 掌握重點

- **角色概念不等於人力保證**：本庫用 AI FTE 表示持續負責一段工作流程的 AI 角色設計；不是已核准的方案、人力或工時保證。
- **定義完整的工作範圍**：定義任務、輸入、工具權限、交付、頻率、成本上限及人工接手。
- **變更後重新檢查品質**：人類擁有決策與例外責任；知識、模型或工具變更後要重跑代表評估。

## 舉個例子

- 情境：每週整理行銷報表的 AI，要能準時交付，也要指出資料缺漏。
- 重點：角色的價值來自穩定交付和例外處理，不能只看生成速度。

## 從這一步開始

寫出角色的任務、頻率、成果、成本上限與人工接手條件。

## 開始前準備

- 要承接的工作、量和頻率、人工基準與品質要求
- 工具／資料範圍、成本、負責人與例外範例

## 依序完成

1. 寫角色契約：觸發、輸入、交付、done、可自主動作及升級條件。
2. 加入排程、去重、重試、觀測及中止開關，先以 shadow mode 比對。
3. 小範圍上線，記錄成功率、每件成本、時間與人工介入率。
4. 建立週期回顧、版本、回復與離職／撤權機制。

## 完成時檢查

- 連續代表批次可追溯；錯誤不靜默、重跑不重複執行外部動作。
- 成效對照基準，人工工作沒有被忽略；未達標可停用與接手。

## 容易忽略的事

- 用 token 數或輸出篇數當唯一績效。
- 沒有責任人就讓 Agent 無期限運作。

## 需要決定的事

定義這個角色可以自行完成哪些事，遇到什麼情況必須交回人類判斷。

# API、MCP 與跨系統自動化

讓系統可靠交換資料，重跑不重複，失敗能追查。

## 這是什麼

跨系統自動化讓資料在工具之間可靠流動。API 是系統提供的操作介面；MCP 讓 Agent 以一致方式使用工具。

適用情境：需要把表單送到 CRM、訂單接到物流，或讓多個工具共用資料時。

## 為什麼重要

- 整合的價值在工作持續正確流動，不只是 API 回傳 200。
- 資料責任與去重規則能避免多份名單、重複訂單或意外寄送。

## 掌握重點

- **資料要有明確來源**：每個欄位指定唯一資料來源，說明同步方向、識別鍵與衝突規則。
- **同步會失敗，也可能重複**：webhook 可能重送、延遲或亂序；驗簽、去重、限流及重試要依平台契約設計。
- **權限和資料可信度分開處理**：外部內容視為不可信資料；工具權限在系統層約束，機密不交給模型自由輸出。

## 舉個例子

- 情境：表單重送兩次，CRM 就建立了兩筆相同商機。
- 重點：同一動作要能被辨認，重試才能補救失敗而不製造重複。

## 從這一步開始

列出資料從哪裡來、要到哪裡去，以及辨認同一筆資料的方式。

## 開始前準備

- 來源和目的系統、API／MCP／CLI 能力與安全連線
- 範例 payload、資料映射、觸發與例外規則

## 依序完成

1. 盤點現有整合，確認 schema、認證、版本、限額和 sandbox。
2. 建欄位映射與 idempotency key，加入驗證、退避重試、失敗佇列與對帳。
3. 測試重送、亂序、部分成功、權限不足與注入內容，隔離真實客戶。
4. 交付流程定義、觀測紀錄、重跑與回復方式；不支援的能力具體回報。

## 完成時檢查

- 同一事件重送不造成重複副作用，最終資料可對帳。
- 失敗有告警與人工負責人，log 不含機密或不必要個資。

## 容易忽略的事

- 對所有錯誤無限重試，造成重複扣款或寄信。
- 兩個系統同時寫入同一欄位，卻沒有衝突規則。

## 需要決定的事

確認資料由誰負責，以及哪些外部動作可以自動執行。

# 品牌定位與訊息架構

先講清楚為誰、解決什麼，以及為什麼選你，再做視覺。

## 這是什麼

品牌定位回答三件事：為誰服務、解決什麼問題、為什麼值得選擇。訊息架構把這些答案安排成容易理解的內容。

適用情境：建立品牌、改版首頁，或團隊對品牌說法不一致時。

## 為什麼重要

- 清楚定位讓網站、廣告與業務說同一件事，減少顧客理解成本。
- 訊息有證據，才不會只剩好聽但無法辨識的形容詞。

## 品牌訊息怎麼形成

 | 概念 | 說明 |
 | --- | --- |
 | 受眾 | 誰在做選擇 |
 | 主張 | 我們解決什麼 |
 | 證據 | 憑什麼相信 |
 | 行動 | 下一步做什麼 |

把這四件事連起來，首頁、簡報和廣告才能使用一致的核心訊息。

## 掌握重點

- **先決定對誰說**：先排受眾與使用情境，再定義類別、差異、可信證據和主要行動。
- **主張要有支持理由**：訊息架構包含核心主張、支持理由、證據與依購買階段安排的內容。
- **語氣要有實際範例**：語氣規則要有實例；中英文依市場重寫，產品事實保持一致。

## 舉個例子

- 情境：品牌首頁同時強調便宜、頂級、快速與客製，讀者抓不到重點。
- 重點：先選主要受眾和最重要的承諾，再用事實支持。

## 從這一步開始

寫出主要受眾，以及他選擇你的最重要理由。

## 開始前準備

- 訪談、客戶研究、既有品牌資產
- 競品與市場、產品事實與可公開證據
- 目標市場、禁用說法、審稿人

## 依序完成

1. 整理受眾問題與競品主張，分開事實、假設和待訪談事項。
2. 提出定位選項及取捨，做首頁／廣告／銷售材料的訊息示例。
3. 輸出一頁定位、訊息層級、語氣與跨語言用語表。

## 完成時檢查

- 主張可追到證據，沒有杜撰客戶、數字或認證。
- 不同載體保有相同定位，CTA 對應受眾下一步。

## 容易忽略的事

- 直接從 logo 或視覺喜好開始。
- 把翻譯當市場策略。

## 需要決定的事

確認品牌定位、主打訊息，以及對外可以承諾的內容。

# CMS、內容模型與多語系

讓內容能被一致地編輯、重用、預覽與安全發布。

## 這是什麼

CMS 是管理網站內容的地方。內容模型把文章、商品、案例等拆成有規則的欄位，讓同一份資料能在多處重用。

適用情境：編輯更新很慢、同一資訊在多頁不一致，或需要多語網站時。

## 為什麼重要

- 結構化內容減少重複輸入，也讓 Agent 能批次整理及驗證。
- 內容有來源、版本和負責人，才不會搬站後變成無人維護的資料。

## 掌握重點

- **先定義內容，再決定欄位**：先定義文章、服務、案例、商品等內容類型，再定欄位、關聯與驗證。
- **多語系不只是翻譯文字**：多語系要定市場、URL、fallback 與翻譯狀態；事實共用、文案依市場調整。
- **編輯、預覽和發布有不同責任**：預覽、發布、審稿和媒體授權要有責任；API 權限與前端顯示分開。

### 名詞小抄

- **CMS**：Content Management System，管理與發布內容的系統。
- **Fallback**：指定內容缺少時，改用哪個備用版本。

## 舉個例子

- 情境：產品名稱出現在首頁、比較表和文章中，卻各自手動輸入。
- 重點：把共用資料集中管理，更新一次就能保持一致。

## 從這一步開始

選一種常更新的內容，列出欄位、來源與使用位置。

## 開始前準備

- 內容與 URL 盤點、欄位與素材
- 語言市場、編輯流程、既有 CMS 與整合

## 依序完成

1. 建立 schema、範例記錄、來源對照與必要欄位驗證。

3. 檢查數量、內容、URL、預覽與權限，再交付編輯流程。

## 完成時檢查

- 重要內容可從舊記錄追到新記錄；缺項有清單。
- 未發布內容不被公開 API 或搜尋意外讀取。

# 商品探索、評論與 App 選型

先解決找不到、看不懂、不敢買，再決定要加哪個工具。

## 這是什麼

商品探索工具幫助顧客找到適合的產品。搜尋、篩選、比較、推薦與評論，各自解決不同的選購疑問。

適用情境：商品很多、規格難比較，或顧客需要更多信任才願意購買時。

## 為什麼重要

- 篩選、比較與可信評論能降低選購成本，尤其是規格多、單價高的商品。
- 每多一個 App 都增加費用、腳本和資料責任；先查原生能力可避免重複。

## 掌握重點

- **搜尋與篩選讓商品容易找到**：Search & Discovery 可管理搜尋、篩選和推薦；headless 需透過 Storefront API 實作對應前台。
- **評論提供可信的經驗**：評論工具如 Judge.me 管收集／審核／展示；XTERRA repo 已有相關整合，不代表每家店都要用。
- **比較與測驗幫助選擇**：比較表／選購測驗依可查證規格給建議；結果不能捏造相容性或產品功效。
- **加購工具要符合商品性質**：加購／組合／訂閱工具依毛利、庫存和需求評估；耐用品不必硬做固定週期訂閱。
- **選工具也要看成本和維護**：每個選型記目的、原生替代、headless 支援、成本、權限、資料匯出與移除方式。

## 舉個例子

- 情境：顧客想找能收納的器材，分類卻只有品牌，找不到適合的選項。
- 重點：依真實選購條件做篩選，比直接增加一個 App 更有用。

## 從這一步開始

整理三個顧客最常問的選購問題，再對應需要的功能。

## 開始前準備

- 商品規格／分類、搜尋詞與零結果、客服疑問和漏斗
- 現有 App／前台架構、費用預算、評論資料與使用權

## 依序完成

1. 把需求分成必備與待評估，先修商品欄位、價格和缺貨規則。
2. 建立篩選／同義詞／比較與推薦樣本，確認商品、配件及變體關聯。
3. 評論搬遷保留來源與狀態，驗證計數、平均分數和隱私；不製造評論。
4. 用代表搜尋、零結果、缺貨、手機與鍵盤測試；查 App API／webhook 和效能影響。

## 完成時檢查

- 可依真實需求找到可買商品；推薦價格／庫存和加入購物車結果一致。
- 評論展示可追溯、無重複；選型表有理由，不只是 App 清單。

## 容易忽略的事

- 以為安裝 theme widget 就能出現在 Astro 前台。
- 把評論平均分數或推薦內容寫死，資料更新後仍顯示舊值。

## 需要決定的事

確認顧客的選購順序、工具費用，以及改善效果是否值得維護成本。

# 電商售後：通知、客服、退貨與保固

訂單成立後仍是顧客旅程，把交付與後續服務一起接通。

## 這是什麼

售後服務連接訂單、出貨、客服、退貨與保固。顧客送出需求後，要能知道進度，也要有明確的人或流程接手。

適用情境：規劃電商上線、客服表單，或處理反覆發生的配送與退貨問題時。

## 為什麼重要

- 找不到訂單、配送或保固資訊，會增加客服成本與退款。
- 表單有成功畫面不代表案件已送達、有人處理或顧客已收到回覆。

## 掌握重點

- **各系統的責任要清楚**：Shopify 管訂單／履約基準；物流、ERP／3PL、客服工單和行銷平台的責任需分開。
- **通知避免漏寄或重寄**：訂單確認、出貨、取消／退款與服務回覆是不同通知；避免多個系統重寄。
- **大型商品有額外配送條件**：大型器材加驗偏遠配送、樓層／搬運、組裝、破損回報與退運成本，規則由商家確認。
- **服務資料與行銷同意分開**：保固／產品註冊需型號、序號與購買資料；服務同意不自動變成行銷訂閱。
- **工具依服務量與流程選擇**：先用原生通知／流程；工單、退貨入口等工具有量或流程需求才加，headless 查 API 支援。

### 名詞小抄

- **ERP**：整合企業營運資料的系統，例如庫存與財務。
- **3PL**：第三方物流服務商。

## 舉個例子

- 情境：顧客送出保固申請，網站顯示成功，客服卻沒有收到。
- 重點：資料被保存和案件被處理是兩件事，兩段都要驗證。

挑一種常見售後需求，畫出提交、收件、處理與回覆流程。

1. 畫訂單到出貨、異常、退貨／退款的狀態與通知責任，定義唯一案件／訂單鍵。

# Design System 與品牌落地

把品牌做成可重用的元件、規則與資產，讓不同畫面維持一致。

## 這是什麼

設計系統把常用的顏色、字級、元件和互動規則整理成共用標準，讓不同人製作的畫面仍像同一個品牌。

適用情境：頁面開始變多、多人協作，或每次都重做相似元件時。

## 為什麼重要

- 共用規則減少同一問題被反覆設計與開發。
- 完整元件狀態讓 Agent 能延伸頁面，同時維持品牌與可用性。

## 掌握重點

- **樣式規則與元件分工**：tokens 定義顏色、字級、間距與動態；元件定義使用情境、狀態和行為。
- **資產要有正確版本**：品牌資產需要版本、授權、正確格式與可使用範圍。
- **必須在真實頁面上成立**：設計規則需落到程式與真實內容；不要只有簡報。

### 名詞小抄

- **Token**：共用樣式值，例如主色、字級與間距。
- **元件 Component**：可重複使用、包含狀態與行為的介面單位。

## 舉個例子

- 情境：三個頁面的主要按鈕有三種藍色、尺寸與錯誤提示。
- 重點：用同一組規則和元件，修改時才能一起更新。

## 從這一步開始

從按鈕、表單和文字層級這三組最常用元素開始整理。

## 開始前準備

- 核准品牌方向、logo、字型與素材授權
- 既有程式庫、頁面種類、內容與語言需求

## 依序完成

1. 盤點重複樣式，建立語意 tokens 與元件清單。
2. 產出按鈕、表單、導覽及內容模組的互動與響應規則。
3. 交付可用元件、範例頁及版本變更紀錄，讓 Agent 以同一來源延伸。

## 完成時檢查

- 真實長短內容、窄螢幕與錯誤狀態可用。
- 設計與程式的 tokens 一致，素材可合法使用。

## 容易忽略的事

- 每一頁各自發明字級和按鈕。
- 未確認授權就把素材交付客戶。

## 需要決定的事

確認視覺方向與共用規則，再讓後續畫面依同一套標準製作。

# 開發交付：功能、品質與可維護性

完成定義包含可用、可測、可交接，不是頁面能打開而已。

## 這是什麼

開發完成代表使用者能順利做完主要任務，也能在失敗時得到清楚回應，後續維護者有辦法接手。

適用情境：準備驗收網站、交接程式，或修正反覆出現的問題時。

## 為什麼重要

- 提早驗證主流程與整合，能降低上線後才發現錯誤的成本。
- 可重現建置與交接能避免只有原開發者修得動。

## 掌握重點

- **驗收看完整旅程**：驗收涵蓋主流程、錯誤狀態、權限、相容性、SEO 與效能。
- **速度要看實際使用情況**：Core Web Vitals 看實際使用者資料；實驗室分數用來診斷，不等於實際表現。
- **測試和正式環境要分開**：開發、staging、production 分離；機密不進前端、版本庫或測試紀錄。

## 舉個例子

- 情境：首頁正常，但付款失敗後畫面沒有任何提示。
- 重點：驗收要看完整流程與失敗情況，不能只看正常畫面。

## 從這一步開始

列出三個最重要的使用任務與各自的失敗情況。

## 開始前準備

- 核准需求、原型、內容、支援裝置與瀏覽器
- 程式庫、API 契約、測試環境與驗收條件

# 電商成長：商品頁、信任與留存

先找漏斗損失，再決定改善商品頁、活動或回購流程。

## 這是什麼

電商成長是找出從進站到回購的流失原因，改善最有影響的一段。流量、成交、毛利和留存需要一起看。

適用情境：有流量卻少成交、活動效果變差，或想提高客單與回購時。

## 為什麼重要

- 流量增加前先修購物障礙，才能避免把預算花在無法成交的體驗上。
- 看毛利、退款與回購，比單看營收更接近成長品質。

## 掌握重點

- **先找到流失的環節**：依來源、裝置與市場看瀏覽 → 加購 → checkout → purchase，先確認資料正確。

- **成長要算進成本與回購**：折扣、訂閱與回購要考慮毛利、庫存、服務成本和退訂。

## 舉個例子

- 情境：很多人加購後離開，可能是結帳時才看到高運費。
- 重點：先找流失發生在哪一步，再提出可驗證的改善假設。

- 活動規則、庫存、受眾同意與品牌素材

## 依序完成

1. 分解漏斗與高價值商品，提出依影響與證據排序的假設。
2. 產出商品頁、活動或留存流程草案，先修功能及資料問題。
3. 設定實驗的主要指標、保護指標、期間與樣本判讀方式。

## 完成時檢查

- 主要購物與退款路徑可用，事件及營收對帳合理。
- 結論附樣本與限制，不把促銷或季節因素誤認成因果。

# 電商上線：標準交付與驗收

每次開店都帶這份清單，逐項交付交易、搜尋、量測與營運證據。

## 這是什麼

電商上線是一份跨部門的交付：能正確交易、被找到、量到成效，也有人處理出貨和售後。

適用情境：商店準備正式開放、搬站切換，或需要統一上線驗收標準時。

## 為什麼重要

- 能下單只是起點；漏掉追蹤、配送或通知，上線後仍會損失收入。
- 固定交付基線讓每個專案不用重新發明檢查清單。

## 電商上線的四個面向

 | 概念 | 說明 |
 | --- | --- |
 | 交易 | 商品、付款、配送與退款 |
 | 搜尋 | 網址、索引與舊站轉址 |
 | 量測 | 購物事件與廣告回報 |
 | 營運 | 通知、客服與維護責任 |

四個面向都要有狀態與證據，才能做上線決定。

## 掌握重點

- **交易能正確完成**：交易必查：商品／庫存、付款／失敗／退款、折扣、配送／稅額、政策與訂單通知。
- **搜尋資產能接續**：搜尋必查：舊 URL／301、canonical、title／description／OG、結構化資料、robots／sitemap 與 GSC。
- **成效有可靠紀錄**：量測預設列 GA4 電商漏斗、Google Ads 轉換、Meta Pixel／CAPI、商品 Feed、consent 與去重。
- **上線後有人接手**：營運必查：Email 名單／自動化、客服／保固入口、DNS／TLS、效能／無障礙、告警與回復。
- **每項都有明確狀態**：每項填完成／阻塞／有理由不適用；尚未投放的渠道保留接線計畫，不自動花廣告費。

## 舉個例子

- 情境：網站可以下單，但廣告購買事件漏記，客服也收不到詢問。
- 重點：每個環節都要有完成證據，才能判斷是否準備好上線。

## 從這一步開始

先建立交易、搜尋、量測、營運四欄清單，標出目前缺口。

## 完成時檢查

- 交易、SEO、量測、觸達與維運各有可重查的證據；阻塞項已有 go／no-go 決定。

# GA4 電商：事件與轉換率怎麼算

讓商品瀏覽、加購、結帳與成交形成可對帳的漏斗。

## 這是什麼

GA4 用事件記錄顧客在網站做了什麼。把瀏覽、加購、結帳和購買連起來，就能看到電商漏斗。

適用情境：需要檢查購物流失、計算轉換率，或驗證網站是否正確記錄成交時。

## 為什麼重要

- 知道哪一步流失，才知道應修商品頁、購物車還是結帳。
- 分母、金額與事件不一致，會讓團隊做出相反的成效判斷。

## 把購物旅程連起來

 | 概念 | 說明 |
 | --- | --- |
 | 看商品 | view_item |
 | 加入購物車 | add_to_cart |
 | 開始結帳 | begin_checkout |
 | 完成購買 | purchase |

每一段都能觀察流失。示意只列主要事件；付款失敗不算購買。

## 掌握重點

- **記錄購物的關鍵動作**：核心事件：view_item_list／select_item、view_item、add_to_cart、begin_checkout、purchase、refund；依實際旅程補 shipping／payment。
- **每筆事件帶上對帳資料**：事件契約記觸發點、item_id、items、value、currency；purchase／refund 用穩定 transaction_id 對回訂單。
- **先說清楚轉換率分母**：購買 session 轉換率＝含 purchase 的 sessions／同範圍 sessions；訂單數／sessions 與所有 key event rate 是不同指標。
- **比較時使用相同範圍**：例如 10,000 sessions 中 100 個完成購買＝1%；先對齊時區、裝置、市場、期間與 consent 覆蓋。
- **不同平台有不同觀察口徑**：GA4、Shopify、Ads 各有歸因和追蹤限制；訂單帳務為交易基準，不要求報表數字完全一樣。

### 名詞小抄

- **事件 Event**：一次可記錄的動作，例如加購或購買。
- **造訪 Session**：同一次使用期間的一組網站互動；一位使用者可以有多次造訪。
- **交易編號 transaction_id**：用來辨認同一筆訂單，避免重複計算。

## 舉個例子

- 情境：10,000 次造訪中，有 100 次造訪完成購買，購買造訪轉換率就是 1%。
- 重點：要先說清楚分母是造訪、使用者還是其他基準，數字才可比較。

## 從這一步開始

先和團隊確認「購買」與「轉換率」的定義，再檢查事件。

## 開始前準備

- 既有 property／data stream、事件來源與測試環境
- 商品／變體 ID 對照、金額含稅運費規則與去識別測試訂單

## 依序完成

1. 建立事件／參數／唯一發送者對照，先查原生整合，補足自訂前台到 hosted checkout 的缺口。
2. 驗證跨域與來源延續，避免把支付商或自己店鋪誤當新來源；分析不得傳 Email 等個資。
3. 在 DebugView／網路請求與後台驗證事件順序、金額、幣別；測重載、付款失敗、退款與 consent。
4. 交付漏斗與指標字典，註明分子分母、排除測試流量及差異原因。

## 完成時檢查

- 同一訂單重載不多記 purchase；退款能對回原交易。
- 報表可按渠道／裝置看漏斗，並能重算定義好的購買轉換率。

## 容易忽略的事

- 按結帳按鈕就送 purchase，或把付款失敗算成交。
- 直接用訂單數除使用者，卻稱為 session 轉換率。

## 需要決定的事

確認怎麼算成交、營收與轉換率，讓團隊使用相同口徑。

# Google Ads 與商品 Feed：先接對再投放

把轉換、商品資料與落地頁對齊，才有可靠的搜尋與購物廣告。

## 這是什麼

Google Ads 負責廣告投放，Merchant Center 提供商品目錄。商品資料與購買回報正確，廣告才有可用的基礎。

適用情境：準備 Google 購物廣告、商品被拒登，或購買轉換重複計算時。

## 為什麼重要

- 缺轉換會讓出價缺乏訊號；錯誤 Feed 會造成商品拒登或錯價。
- 把接線和投放分開驗收，能避免有花費卻無法判讀成效。

## 掌握重點

- **先分清每個平台的工作**：Ads 管投放／轉換；Merchant Center 管商品資料與資格；GA4 分析行為，GSC 看搜尋索引。
- **避免重複主要購買轉換**：同一購買避免原生 Ads 與 GA4 匯入同時作主要出價轉換；觀察用來源需檢查目標納入規則。
- **商品目錄要與網站一致**：Feed 對齊穩定 id、品牌／GTIN 等適用識別碼、價格／幣別、庫存、圖片、正式落地頁與運退規則。
- **進階比對需要正確資料用途**：Enhanced conversions 用核准的第一方資料補強比對；雜湊不是免除同意或資料責任。
- **官方整合仍要驗證完整旅程**：Shopify Google & YouTube 是可優先評估的官方整合；headless 的結帳／域名／商品連結仍要實測。

### 名詞小抄

- **Feed**：提供給平台的結構化商品目錄。
- **GTIN**：商品的全球貿易識別碼，依品項與平台規則提供。
- **主要轉換**：廣告出價主要使用的成果訊號，例如購買。

## 舉個例子

- 情境：商品目錄寫有庫存，落地頁卻顯示售完，可能影響刊登資格。

確認 Ads、Merchant Center 和 GA4 的現有帳號與連結關係。

- 既有 Ads／Merchant Center／GA4 帳號與目標市場
- 商品識別碼、運費退貨政策、主要轉換定義及授權範圍

## 依序完成

3. 測試訂單對帳、重載去重、跨域／歸因及 consent；Enhanced conversions 依現行能力驗證。
4. 交付商品資格、拒登原因與修正清單；預算、素材、活動啟用另依既有投放授權。

## 完成時檢查

- 代表商品價格／庫存／網址與落地頁一致，拒登項有原因及處置。
- 一次購買只產生預期的主要出價訊號；接線完成不宣稱已產生成效。

## 容易忽略的事

- 同一筆訂單在多個主要 conversion actions 重複計算。
- Feed 指向 Shopify theme，但實際買家應前往自訂前台。

# Hosting、DNS、CDN 與環境

釐清服務由誰代管，以及域名、應用、資料和郵件如何連在一起。

## 這是什麼

網站能被打開，仰賴域名、DNS、主機、內容與網路服務一起運作。知道各層的責任，才能選型、維護與排錯。

適用情境：規劃代管、更換網域，或遇到網站／郵件連線問題時。

## 為什麼重要

- 主機選擇影響可用性、費用、維護責任與事故回復。
- 知道域名、DNS 和郵件的關係，能避免搬站時一起弄壞公司信箱。

## 從輸入網址到打開網站

 | 概念 | 說明 |
 | --- | --- |
 | 域名與 DNS | 找到服務位置 |
 | CDN／網站主機 | 接收與處理請求 |
 | 應用與內容 | 產生可讀的頁面 |

簡化的請求路徑；實際平台可能合併多層。郵件服務另有 DNS 紀錄。

## 掌握重點

- **代管範圍依平台與合約決定**：Shopify／Webflow 平台代管與 VPS／雲端自管的責任不同；由實際合約界定。
- **先分清系統層次**：域名註冊、DNS、CDN、TLS、應用與資料庫分層管理，不把所有問題當主機問題。
- **環境、備份與回復一起規劃**：定義 dev／staging／prod、資料區域、RTO／RPO、備份與監控；流量和費用估算註明假設。

### 名詞小抄

- **DNS**：把域名連到網站、郵件等服務的查詢紀錄。
- **CDN**：把內容放在不同地區節點，加快傳送的服務。
- **TLS**：瀏覽器與網站之間的加密連線機制。

## 舉個例子

- 情境：搬網站時改了 DNS，卻一起覆蓋郵件紀錄，造成信件收不到。
- 重點：網站和郵件共用域名，但各自的紀錄與責任需要分開確認。

## 從這一步開始

先畫出域名、DNS、網站、資料和郵件分別由誰管理。

## 開始前準備

- 應用架構、流量與資料類型、目前 DNS 區域
- 帳號擁有人、預算、SLA、備份與復原需求

## 依序完成

1. 整理架構、DNS 與第三方依賴，標明平台／Tenten／客戶責任。
2. 比較代管與自管、成本和擴充方式；盤點 CDN、TLS 和資料持久化。
3. 產出環境配置、備份／回復、監控和存取交接方案。

## 完成時檢查

- 正式域名與 TLS 正常，MX／TXT 等郵件紀錄保留。
- 重啟／重建不遺失持久資料，備份有隔離回復證據。

## 容易忽略的事

- 把 DNS TTL 當保證立即切換。
- 只備份程式，沒有資料庫和媒體。

## 需要決定的事

確認預算、可用性與資料存放條件，並指定每一層的維護責任。

# Klaviyo：從電子報到自動化旅程

用訂閱與購物行為，安排歡迎信、棄單提醒和購後教學。

## 這是什麼

Klaviyo 是電商的 Email／SMS 自動化工具。它根據訂閱和購物行為，把合適的訊息送給合適的人。

適用情境：想做歡迎信、棄單提醒、購後教學，或讓電子報更有相關性時。

## 為什麼重要

- 不用每次手動群發；依訂閱、購物和售後狀態提供相關訊息。
- 好的停止條件能避免已購買仍收棄單信、已退訂仍被打擾。

## 一位訂閱者的訊息旅程

 | 概念 | 說明 |
 | --- | --- |
 | 同意訂閱 | 進入歡迎流程 |
 | 了解商品 | 收到相關內容 |
 | 完成購買 | 退出該次棄單提醒 |
 | 開始使用 | 接續購後教學 |

這是一個流程設計範例。每封行銷訊息都需符合訂閱狀態；退訂後停止行銷寄送。

## 掌握重點

- **先認識人、名單與流程**：Klaviyo 是 Email／SMS 與旅程平台；Profile 是人、List 是名單、Segment 是動態條件、Flow 是事件觸發流程、Campaign 是單次活動。
- **有 Email 不代表能寄行銷信**：有 Email／Profile 不等於同意行銷；Email 與 SMS 同意分開，訂單／服務通知另有用途。
- **從最有用的旅程開始**：先做 Welcome、Checkout 棄單、購後教學；再評估瀏覽提醒、回購／winback。大型耐用品優先教學、保養與配件。
- **事件發生不代表所有狀態相同**：原生 Checkout Started／Placed Order 與自訂表單事件分開；Placed Order 不保證已收款，付款／取消／退款狀態另查。
- **退訂必須在各系統生效**：不能假設退訂雙向同步：官方說明 Shopify 退訂不會自動退訂 Klaviyo，需明確處理來源與抑制。

### 名詞小抄

- **Profile／List**：Profile 是一個人的資料；List 是收納成員的名單。
- **Segment**：依條件自動變動的分群，例如最近購買的已訂閱顧客。
- **Flow／Campaign**：Flow 依條件自動觸發；Campaign 是指定時間的一次活動。

## 舉個例子

- 情境：顧客同意訂閱後收到歡迎信；後來完成購買，就改接購後教學。
- 重點：流程要隨顧客狀態改變，已購買的人應停止收到同一購物流程的棄單提醒。

## 從這一步開始

先選一條旅程，寫下觸發條件、要傳的訊息，以及何時停止。

## 開始前準備

- 既有寄送平台／Shopify 整合、名單來源、同意／退訂紀錄
- 寄件域名、品牌素材、流程目標與可收測試信的內部名單

## 依序完成

1. 盤點現有平台與 live／draft 流程，畫原生訂單和自訂表單資料流；先防重複串接／寄送。

3. 測訂閱／未同意、購買後退出棄單、退訂抑制與重試去重；歷史匯入隔離 welcome 觸發。
4. 透過受支援 API／整合完成可做部分，交付測試收件證據、草稿與未支援能力；寄送依任務授權。

## 完成時檢查

- Profile／事件／訂閱狀態可分別驗證；內部測試信內容和連結正確。
- 買後停止提醒、退訂不再行銷；記錄兩端不同步的處置。
- 用點擊／有效訂單／退訂判讀；平台歸因營收不直接當增量營收。

## 容易忽略的事

- 啟用 Klaviyo 和 Shopify 兩套棄單流程。

# 網站上線：一次看完必要條件

上線前一次確認 SEO、交易、追蹤、DNS 與回復方案。

## 這是什麼

網站上線是把通過驗收的版本切到正式環境，並確認使用者、搜尋引擎與營運流程都能正常接續。

適用情境：準備發布新站、改版切換，或需要決定能否正式上線時。

## 為什麼重要

- 上線是一次系統切換，漏一個環節就可能造成流量、交易或資料損失。
- 有明確 go／no-go 與回復條件，團隊才能快速決定。

## 掌握重點

- **上線要看整套系統**：至少涵蓋功能、內容、SEO、量測、隱私、DNS／TLS、效能、備份和責任交接。
- **既有搜尋與量測要接續**：GA4／GSC 先盤點沿用；Google Ads／Meta 依實際渠道啟用；title、description、OG tags 分開查。
- **正式環境需要再次驗證**：預覽站不是正式站；production 的索引、表單、付款與追蹤需再驗證。

## 舉個例子

- 情境：預覽站表單正常，上線後正式環境卻缺少接收設定。
- 重點：上線前測試，切換後還要在正式網址再驗證。

## 從這一步開始

把必要項目列成通過、未通過與待決定三種狀態。

## 開始前準備

- 核准版本、網域與上線窗口、決策及維運聯絡人
- 驗收、301、事件、DNS、備份與回復計畫

## 依序完成

1. 整理 go／no-go 表，先驗證 staging 主流程、SEO、量測及必要政策。
2. 盤點正式 DNS／TLS／郵件、資料同步、環境變數與監控，準備可回復版本。
3. 在既有上線授權內執行切換，依適用情境移除 production noindex／密碼保護。
4. 檢查代表 URL、訂單或表單、事件與 GSC；交付帶時間和版本的上線收據及觀察表。

## 完成時檢查

- 正式站主要任務成功；舊 URL 對應正確；分析事件去重。
- 沒有 staging 限制殘留；監控與責任人已交接；未通過項有明確決定。

## 容易忽略的事

- 全站解除保護，連後台和預覽內容一起公開。
- 只看首頁，沒測表單、購物或 redirect。

## 需要決定的事

依驗收結果決定是否上線，並確認誰能決定暫停或回復。

# CRM、Email 與客戶旅程

把名單、成交和後續服務連起來，避免商機在交接時遺失。

## 這是什麼

CRM 記錄客戶與商機狀態；客戶旅程則決定在什麼時候，提供什麼資訊或服務，讓交接不遺漏。

適用情境：網站開始收詢問、名單分散，或需要規劃後續 Email 與回訪時。

## 為什麼重要

- 網站有表單還不夠；商機要送到對的人並能追蹤後續結果。
- 有同意、分群與停止條件的旅程，能提升相關性並降低打擾。

## 掌握重點

- **客戶資料需要共用定義**：定義 contact、company、deal、來源與生命週期，指定欄位資料來源和去重鍵。
- **行銷與服務各有不同規則**：訂單通知與行銷分開；同意、退訂、退信及刪除需定義跨系統責任，不假設平台自動雙向同步。
- **寄信還需要正確的域名設定**：Email 交付須驗證寄件域名與 SPF／DKIM／DMARC；改 DNS 時保留既有郵件服務。

## 舉個例子

- 情境：同一個詢問在表單和試算表各存一份，沒人知道誰已回覆。
- 重點：把資料來源、處理責任和狀態連起來，才能接續服務。

## 從這一步開始

畫出一筆詢問從進站到成交的流程，標出每個交接點。

## 開始前準備

- 名單欄位、來源、同意紀錄、CRM 及寄送平台
- 旅程、負責人、回應時限、訊息與停止條件

## 依序完成

1. 建立欄位映射、分群、分派與重複資料處理規則。
2. 產出歡迎、詢價、棄單或回購流程及訊息草稿。
3. 以測試名單驗證觸發、排除、退訂、去重及 CRM 更新。

## 完成時檢查

- 每筆有效表單進正確系統並有負責人；重送不重複建立。
- 退訂後不再收到不適用的行銷流程；測試不寄給真實客戶。

## 容易忽略的事

- 把所有歷史客戶視為已同意行銷。
- 匯入資料時意外觸發大量信件。

## 需要決定的事

確認名單用途、訊息內容與寄送範圍，再啟用已驗證的流程。

# 上線量測：GA4、GSC、Google Ads 與 Meta

先釐清要量什麼，再接好流量、行為與成交資料。

## 這是什麼

量測是把網站行為轉成可判斷的資料。GA4、GSC 和廣告平台各看不同環節，合起來才能理解成效。

適用情境：網站上線、活動開始，或團隊需要回答「流量從哪來、為什麼沒有成交」時。

## 為什麼重要

- 沒有可靠量測，上線後無法判斷流量與活動是否帶來成果。
- 重複 purchase、幣別或 consent 錯誤會直接影響廣告優化和商業判讀。

## 四個工具，四種問題

 | 概念 | 說明 |
 | --- | --- |
 | GSC | 搜尋結果有沒有被看見、點進來？ |
 | GA4 | 進站後做了什麼、在哪裡離開？ |
 | Google Ads | Google 廣告帶來什麼成果？ |
 | Meta | Facebook／Instagram 廣告帶來什麼成果？ |

先決定想回答的問題，再選工具與事件。各平台的歸因方式不同。

## 掌握重點

- **不同工具回答不同問題**：GA4 看行為；GSC 看 Google 搜尋與索引；Google Ads／Meta 看投放與轉換，各自有不同歸因。
- **追蹤碼與 SEO 標籤各有用途**：SEO title／description、OG tags 與 Meta Pixel 是不同東西；GTM 是可選部署工具，不是全部追蹤。
- **事件名稱和成交定義要一致**：電商事件要定義觸發點、transaction_id、items、value、currency；個資不能隨意送進分析。

### 名詞小抄

- **GA4**：Google Analytics 4，觀察進站後的行為與轉換。
- **GSC**：Google Search Console，觀察 Google 搜尋曝光、點擊與索引。
- **GTM**：Google Tag Manager，用來管理追蹤標籤的工具。

## 舉個例子

- 情境：GSC 顯示搜尋點擊增加，GA4 卻顯示訪客在商品頁離開。
- 重點：前者回答能否被找到，後者幫忙定位進站後的問題。

## 從這一步開始

先列出最想回答的三個商業問題，再決定需要哪些事件。

## 開始前準備

- 既有 GA4／GSC／GTM／廣告帳號 ID 與授權連線
- 事件、成交定義、來源系統、測試訂單及市場隱私要求

## 依序完成

1. 先盤點現有原生 App、theme、GTM 和 server-side 實作，畫唯一事件責任表。
2. GA4／GSC 與 Google Ads／Meta 都列標準盤點；依渠道計畫接線，未使用者註明理由及未來需求，不直接略過。
3. 測試 consent 接受／拒絕、購買、退款與重複載入；Meta Pixel／CAPI 以相同 event_name／event_id 去重。
4. 比對 DebugView／平台測試事件與實際訂單，保留 payload、時間及去重證據；說明歸因差異。

## 完成時檢查

- 一筆測試訂單只有一筆有效成交，金額幣別與訂單一致。
- 同意與拒絕行為符合核准規則；報表不暴露個資。

## 容易忽略的事

- 只確認 tag 有載入，沒測事件。
- 重建既有 property，導致歷史資料斷開。

## 需要決定的事

確認哪些行為代表成果，以及資料收集與同意規則。

# Meta：Pixel、CAPI 與成交去重

把廣告接到真實購買，避免瀏覽器與伺服器把一單算兩次。

## 這是什麼

Meta 追蹤把網站購買回傳給 Facebook／Instagram 廣告系統。Pixel 從瀏覽器回傳，CAPI 從伺服器回傳。

適用情境：準備 Meta 廣告，或廣告報表的購買數看起來不合理時。

## 為什麼重要

- 可用的購買事件能幫廣告學習與評估；錯誤訊號會浪費預算。
- 瀏覽器與伺服器互補，但重複購買會把 ROAS 虛增。

## 兩個來源，同一筆購買

 | 概念 | 說明 |
 | --- | --- |
 | 瀏覽器 Pixel | 事件名稱＋eventID |
 | 伺服器 CAPI | 相同名稱＋event_id |
 | Meta 去重 | 辨認為同一筆購買 |

兩路使用相同事件識別值；是否正確去重仍要在平台測試。

## 掌握重點

- **兩種回傳方式互相補足**：Pixel 收瀏覽器事件；CAPI 收伺服器事件。它們不同於 SEO meta／OG tags。
- **先接好主要購物動作**：核心路徑含 ViewContent、AddToCart、InitiateCheckout、Purchase；value／currency 和商品 ID 要一致。
- **同一事件要能互相辨認**：同一事件送兩路時，對齊 event_name；瀏覽器 eventID 對上伺服器 event_id，同一次動作用同一穩定值。
- **客製前台要額外確認**：Shopify 官方 Meta 渠道可處理部分事件；headless 自訂前台的覆蓋需另外確認。
- **資料分享遵守同意範圍**：CAPI 不等於免 consent；分享層級、顧客資料與用途必須符合核准規則。

### 名詞小抄

- **Pixel**：在瀏覽器內收集並回傳事件的程式。
- **CAPI**：Conversions API，由伺服器回傳事件的介面。
- **去重 Deduplication**：辨認多份回報其實是同一次動作，只計算一次。

## 舉個例子

- 情境：同一筆購買由 Pixel 和 CAPI 各送一次，卻沒有共用識別碼。
- 重點：把兩份回報認成同一事件，才能避免一單算兩次。

## 從這一步開始

查現有 Pixel、CAPI 與官方整合，標出每個事件由誰發送。

## 開始前準備

- 既有 Business／廣告帳號、Pixel／dataset、目錄及連線權限
- 事件責任表、商品 ID 對照、同意規則和測試訂單

## 依序完成

1. 盤點官方渠道、GTM、程式與 server 實作，只保留明確的事件發送責任。
2. 依現行 API／原生整合完成授權內配置；商品事件 content_ids 對齊廣告目錄。
3. 用 Test Events／診斷驗證購買、拒絕同意、重載與重試；查 browser／server 配對及去重。
4. 交付去識別 payload、時間、事件 ID 配對與金額對帳，列出尚未覆蓋的旅程。

## 完成時檢查

- 一筆測試購買在平台形成一筆有效轉換；兩路事件有配對證據。
- 拒絕分享時的行為符合規則，事件中沒有額外洩漏客戶資料。

## 容易忽略的事

- 官方 App 和手動 Pixel 同時重複發送。
- 每次重試產生新 event_id，或只看 Pixel Helper 亮綠燈。

## 需要決定的事

確認資料分享與渠道用途；追蹤接通和啟用廣告是兩個分開的決定。

- [Meta：Pixel 與 CAPI 去重](https://developers.facebook.com/documentation/ads-commerce/conversions-api/deduplicate-pixel-and-server-events)（2026-10-21）：同一事件的名稱與 eventID／event_id 配對及去重驗證；不代表已檢查客戶帳號。

# Magento → Shopify：網站搬家

保住商品、交易、搜尋與量測；搬站要有對照表、演練與回復條件。

## 這是什麼

搬站是把既有網站的商品、內容、客戶關係和搜尋入口移到新系統，並讓使用者能繼續完成原本的事。

適用情境：從 Magento 換到 Shopify，或更換平台與網址結構時。

## 為什麼重要

- 舊 URL、搜尋流量與交易資料都是資產；遺漏會造成流量、營收及營運中斷。
- 先演練、再增量同步與切換，能把風險留在可回復的階段。

## 舊的搜尋入口如何接續

 | 概念 | 說明 |
 | --- | --- |
 | 舊商品網址 | 搜尋結果或既有連結 |
 | 301 轉址 | 在實際路由層處理 |
 | 對應新商品頁 | 內容相關、可正常開啟 |

有對應頁才導向；沒有合適替代內容時，依情況保留 404／410，不一律送到首頁。

## 掌握重點

- **先知道有哪些資產**：先盤點 URL、流量頁、商品／變體、客戶、訂單、媒體、折扣與系統整合。
- **舊入口要通往正確新頁**：舊 URL 永久導向最相關新頁；無對應回 404／410。Headless 在實際接收域名的路由層驗證，不能只匯入 Shopify。
- **帳號和歷史資料要個別驗證**：客戶登入與密碼不能假定可直接搬；歷史訂單、禮卡和通知副作用需逐項驗證。

## 舉個例子

- 情境：舊搜尋結果仍指向某個商品網址，新站卻找不到那一頁。
- 重點：建立舊網址到新網址的對照與轉址，才能接住既有流量。

## 從這一步開始

先列出要搬的資料，以及最有流量或營收價值的舊網址。

## 開始前準備

- 舊站與目標店網址、可用匯出資料、流量及網址清單

# 維運、安全與事故回復

監控看得到問題，備份真的能還原，事故有人做決策。

## 這是什麼

維運讓服務持續可用；事故準備則讓問題發生時，團隊知道如何發現、處理與恢復，並減少資料損失。

適用情境：接手網站代管、規劃備份，或需要讓事故處理不再依賴某一個人時。

## 為什麼重要

- 備份存在不代表能回復；事故時需要可操作的流程和證據。
- 最小權限與環境隔離可降低錯誤或外洩的影響範圍。

## 掌握重點

- **先定能承受的中斷與資料損失**：RTO 是可接受回復時間，RPO 是可接受資料損失窗口；由商業需求決定。
- **權限需要持續整理**：帳號和機密走安全連線；離職、供應商與 Agent 權限需撤銷和定期盤點。
- **監控與更新要能發現問題**：監控至少看可用性、關鍵任務、錯誤與備份；更新先檢相容性並保留回復方式。

### 名詞小抄

- **RTO**：可接受的服務回復時間。
- **RPO**：可接受的資料損失時間範圍。

## 舉個例子

- 情境：每天都有備份，真正故障時卻發現資料無法還原。
- 重點：備份存在和可以恢復服務是兩回事，還原要實際演練。

## 從這一步開始

先決定服務能中斷多久、可接受多少資料損失，再檢查備份。

## 開始前準備

- 系統及權限清單、備份位置、回復需求
- 事件負責人、聯絡路徑、變更窗口與合約責任

## 依序完成

1. 驗證最小權限、資料保存與更新流程，記錄可修正風險。
2. 在隔離環境做還原演練，量測時間與資料缺口。
3. 建立有閾值、通知與升級人的監控；測試告警是否真的送達。
4. 事故先穩定服務和保留證據，記錄時間線、影響、修復及後續行動。

## 完成時檢查

- 有實際 restore 結果；告警能到正確值班角色。
- 事故與變更有版本、責任人及可追溯紀錄，不在收據洩露機密。

## 容易忽略的事

- 承諾未簽訂的 24／7 或回應 SLA。
- 用刪除記錄掩蓋故障，或未對帳就回復舊資料。

## 需要決定的事

確認事故由誰決策、如何溝通，以及服務中斷與資料損失的可接受範圍。

# Google Ads、Meta 與廣告交付

先接好目標、量測與 landing page，再開始花預算。

## 這是什麼

付費廣告用預算取得目標受眾的注意，再透過合適的頁面促成詢問或購買。評估時要看商業成果與成本。

適用情境：規劃 Google／Meta 活動、調整預算，或判斷活動是否值得繼續時。

## 為什麼重要

- 投放不能修復錯的商品訊息與壞掉的成交流程。
- 明確預算與保護指標，才能控制實驗成本。

## 掌握重點

- **先定義真正的成果**：依商業目標選主轉換，區分 primary 與觀察事件，避免把多個同義事件都當成果。
- **廣告與落地頁必須一致**：受眾、訊息、素材與 landing page 要一致；UTM 與命名便於跨渠道比對。
- **收入指標要一起看成本**：ROAS、CAC 需一起看毛利、退貨、歸因與新客；平台報表不等於增量貢獻。

### 名詞小抄

- **ROAS**：廣告歸因收入除以廣告費，不等於利潤。
- **CAC**：取得一位新客戶的成本，需先定義包含哪些費用。
- **Landing page**：點擊廣告後到達的頁面。

## 舉個例子

- 情境：廣告說免運，落地頁卻有運費限制，點擊增加但成交很差。

- 帳號、轉換、受眾同意、品牌素材與目的頁

## 依序完成

2. 產出 campaign 結構、素材、UTM、排除條件與測試計畫。
3. 驗證目的頁、事件、金額與預算；依任務已有授權發布或交付草稿。
4. 提出觀察節奏與停損條件，不因單日波動自動做大幅調整。

## 完成時檢查

- 主要轉換只有一個明確計算來源，目的頁可完成任務。
- 報告包含花費、有效成果、樣本限制及下一個可測假設。

# Shopify 開店：先接通營運

先確認商品、訂單與市場規則，再做店面和 App。

## 這是什麼

Shopify 是電商的交易與營運中心，管理商品、訂單、付款和庫存。開店時要先確認每一筆交易如何被正確處理。

適用情境：建立新店、接手現有商店，或要增加市場與物流整合時。

## 為什麼重要

- 外觀完成不代表能正確收款、出貨或退款。
- 商品與系統資料有一致定義，才能降低庫存、價格與訂單錯誤。

## 掌握重點

- **商品與庫存以誰的資料為準**：SKU／variant 是可銷售單位；商品、庫存、訂單各指定唯一資料來源，ERP／3PL 寫入不可互相覆蓋。
- **市場決定交易規則**：市場決定語言、幣別、價格、可售區、稅、支付與配送；法規與稅務由商家專業負責人確認。
- **先查原生功能，再選 App**：先用原生能力，再依需求加 App；checkout、API 與 Markets 能力須驗證當前方案。

### 名詞小抄

- **SKU**：辨認可銷售品項的內部編碼。
- **Variant**：商品的特定規格組合，例如顏色與尺寸。

## 舉個例子

- 情境：客人成功付款，但訂單的運費和庫存數量不正確。
- 重點：商品、價格、金物流與庫存規則必須一起驗證。

## 從這一步開始

挑一個代表商品，寫出它從上架到出貨、退款的完整流程。

## 開始前準備

- 商品樣本、SKU／庫存來源、既有訂單與客戶需求
- 市場、金流物流、退換貨、稅務與營運負責人

## 依序完成

1. 建商品欄位和市場矩陣，記錄每欄唯一資料來源。
2. 提出 theme、App 與整合方案，說明費用、資料權限與移除方式。
3. 驗證成功／失敗付款、運費／稅額、折扣、缺貨、部分退款／退貨、庫存回補與通知；大型商品抽測不可配送地址。

## 完成時檢查

- 代表商品與市場的測試單金額、幣別、運費及稅額符合核准規則。
- 庫存、訂單與追蹤事件一致；測試資料不混入正式營收。

## 容易忽略的事

- 把稅務設定成功當成法遵已完成。
- 用重複 App 安裝換取功能，卻沒有資料責任。

# Technical SEO 與 301 Redirect

讓搜尋引擎找到正確頁面，並保留改版前累積的搜尋資產。

## 這是什麼

技術 SEO 讓搜尋引擎能找到、讀懂並收錄正確頁面。改版時的 301 轉址，則把舊入口接到新位置。

適用情境：網站新上線、網址變更、搜尋流量下降，或重要頁面沒有被收錄時。

## 為什麼重要

- 搜尋引擎看不到或選錯 URL，再好的內容也無法穩定帶來自然流量。
- 搬站有正確對應與監測，能降低遺漏與排錯成本；排名仍可能短期波動。

## 掌握重點

- **抓取、索引與主要版本不同**：robots 控制抓取；noindex 控制索引，需允許爬蟲讀到；canonical 提示主要版本。
- **提供清楚的網站與語言結構**：sitemap 放標準且可索引 URL；多語市場檢查 hreflang、自我 canonical 與互相對應。
- **搬家時保留正確轉址**：301／308 用於永久搬移；保留最相關一對一映射，Google 建議 redirect 至少維持一年，能長留則長留。

### 名詞小抄

- **索引 Index**：搜尋引擎收錄並可用來產生搜尋結果的頁面資料。
- **Canonical**：告訴搜尋引擎多個相似網址中，哪個是建議的主要版本。
- **301 Redirect**：把舊網址永久轉向新網址。

## 舉個例子

- 情境：正式站沿用預覽站的 noindex，搜尋引擎就不會把頁面納入索引。
- 重點：上線時要確認搜尋限制已在正確環境解除。

## 從這一步開始

先檢查首頁和一個重要商品頁是否可被抓取與索引。

## 開始前準備

- 正式與舊站 URL、GSC／流量／站內連結清單
- 要索引的範圍、市場語言、平台與 DNS／CDN 限制

## 依序完成

1. 抓取 status、索引指令、canonical、內鏈、sitemap 與結構化資料。
2. 建立舊新 URL 對照，驗證一跳永久導向、目的頁 200、無循環。
3. 修內鏈、metadata 與 sitemap；在授權 GSC property 交 sitemap 並檢查代表 URL。
4. 域名搬遷才評估 Change of Address；保留切換前後索引、流量和 404 觀察。

## 完成時檢查

- 重要頁能抓取與索引；staging 有存取保護，不只依賴 robots。
- redirect、canonical、hreflang 與 sitemap 指向一致，監測附日期。

## 容易忽略的事

- 把所有 404 導到首頁，造成 soft 404。
- 以為提交 sitemap 就保證收錄或排名。

## 需要決定的事

確認哪些內容保留、合併或淘汰，再決定網址與轉址安排。

## 來源與適用範圍

- 建議基線，依專案調整；整理日期：2026-10-21
- [Google Search Central：網站遷移](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)（2026-10-21）：URL 盤點、永久 redirect、canonical、切換、GSC 及至少一年的 redirect 保留建議。
- [Google Search Central：AI 搜尋功能](https://developers.google.com/search/docs/appearance/ai-features)（2026-10-21）：Google AI 搜尋的索引資格、SEO 基礎與不需特殊 schema／AI 文字檔；不能推論其他 AI 平台。

# UX、資訊架構與轉換

讓使用者能找到資訊、理解選擇，並完成真正重要的任務。

## 這是什麼

UX 是使用者完成任務的整體體驗。資訊架構決定資訊放在哪裡；轉換設計則讓下一步清楚、容易完成。

適用情境：使用者找不到資訊、表單填不完，或購物中途離開時。

## 為什麼重要

- 好看但找不到答案的網站，會浪費搜尋與廣告帶來的流量。
- 清楚的路徑、表單與錯誤處理，能減少詢問和放棄。

## 掌握重點

- **以使用者的任務安排內容**：從主要使用任務安排導覽、頁面、內容與 CTA，避免用公司組織圖當架構。
- **每一步都要有狀態回應**：表單與購物流程須有 loading、empty、error、success 及回復狀態。
- **不同裝置與操作方式都要可用**：鍵盤、焦點、標籤、對比與行動裝置是基本交付；轉換率變化須和流量品質一起判讀。

## 舉個例子

- 情境：商品頁有漂亮圖片，卻找不到運費與退貨規則。
- 重點：先補齊影響購買的資訊，比單純換按鈕顏色更有依據。

## 從這一步開始

選一個主要任務，從進站到完成實際走一次。

## 開始前準備

- 優先受眾、主要任務、既有漏斗或客服問題
- 內容盤點、裝置分布、品牌規則

## 依序完成

1. 整理任務流程、sitemap 與頁面內容順序，說明每一步要解決的疑慮。
2. 產出可操作原型，覆蓋主流程與失敗情境。
3. 驗證鍵盤、表單、窄螢幕與 CTA；有足夠流量再規劃實驗。

## 完成時檢查

- 主要任務能從入口走到完成；錯誤可被理解並修復。
- 量測事件與假設一致，改善結果附樣本和期間。

## 容易忽略的事

- 只交桌面首頁。
- 把點擊變多當成商業成果變好。

## 需要決定的事

確認使用者最重要的任務，以及品牌、資訊完整度與操作簡單度的取捨。
