# 品牌定位與訊息架構

先講清楚為誰、解決什麼，以及為什麼選你，再做視覺。

## 這是什麼

品牌定位回答三件事：為誰服務、解決什麼問題、為什麼值得選擇。訊息架構把這些答案安排成容易理解的內容。

適用情境：建立品牌、改版首頁，或團隊對品牌說法不一致時。

## 為什麼重要

- 清楚定位讓網站、廣告與業務說同一件事，減少顧客理解成本。
- 訊息有證據，才不會只剩好聽但無法辨識的形容詞。

## 品牌訊息怎麼形成

 | 概念 | 說明 |
 | --- | --- |
 | 受眾 | 誰在做選擇 |
 | 主張 | 我們解決什麼 |
 | 證據 | 憑什麼相信 |
 | 行動 | 下一步做什麼 |

把這四件事連起來，首頁、簡報和廣告才能使用一致的核心訊息。

## 掌握重點

- **先決定對誰說**：先排受眾與使用情境，再定義類別、差異、可信證據和主要行動。
- **主張要有支持理由**：訊息架構包含核心主張、支持理由、證據與依購買階段安排的內容。
- **語氣要有實際範例**：語氣規則要有實例；中英文依市場重寫，產品事實保持一致。

## 舉個例子

- 情境：品牌首頁同時強調便宜、頂級、快速與客製，讀者抓不到重點。
- 重點：先選主要受眾和最重要的承諾，再用事實支持。

## 從這一步開始

寫出主要受眾，以及他選擇你的最重要理由。

## 開始前準備

- 訪談、客戶研究、既有品牌資產
- 競品與市場、產品事實與可公開證據
- 目標市場、禁用說法、審稿人

## 依序完成

1. 整理受眾問題與競品主張，分開事實、假設和待訪談事項。
2. 提出定位選項及取捨，做首頁／廣告／銷售材料的訊息示例。
3. 輸出一頁定位、訊息層級、語氣與跨語言用語表。

## 完成時檢查

- 主張可追到證據，沒有杜撰客戶、數字或認證。
- 不同載體保有相同定位，CTA 對應受眾下一步。

## 容易忽略的事

- 直接從 logo 或視覺喜好開始。
- 把翻譯當市場策略。

## 需要決定的事

確認品牌定位、主打訊息，以及對外可以承諾的內容。

# UX、資訊架構與轉換

讓使用者能找到資訊、理解選擇，並完成真正重要的任務。

## 這是什麼

UX 是使用者完成任務的整體體驗。資訊架構決定資訊放在哪裡；轉換設計則讓下一步清楚、容易完成。

適用情境：使用者找不到資訊、表單填不完，或購物中途離開時。

## 為什麼重要

- 好看但找不到答案的網站，會浪費搜尋與廣告帶來的流量。
- 清楚的路徑、表單與錯誤處理，能減少詢問和放棄。

## 掌握重點

- **以使用者的任務安排內容**：從主要使用任務安排導覽、頁面、內容與 CTA，避免用公司組織圖當架構。
- **每一步都要有狀態回應**：表單與購物流程須有 loading、empty、error、success 及回復狀態。
- **不同裝置與操作方式都要可用**：鍵盤、焦點、標籤、對比與行動裝置是基本交付；轉換率變化須和流量品質一起判讀。

## 舉個例子

- 情境：商品頁有漂亮圖片，卻找不到運費與退貨規則。
- 重點：先補齊影響購買的資訊，比單純換按鈕顏色更有依據。

## 從這一步開始

選一個主要任務，從進站到完成實際走一次。

## 開始前準備

- 優先受眾、主要任務、既有漏斗或客服問題
- 內容盤點、裝置分布、品牌規則

## 依序完成

1. 整理任務流程、sitemap 與頁面內容順序，說明每一步要解決的疑慮。
2. 產出可操作原型，覆蓋主流程與失敗情境。
3. 驗證鍵盤、表單、窄螢幕與 CTA；有足夠流量再規劃實驗。

## 完成時檢查

- 主要任務能從入口走到完成；錯誤可被理解並修復。
- 量測事件與假設一致，改善結果附樣本和期間。

## 容易忽略的事

- 只交桌面首頁。
- 把點擊變多當成商業成果變好。

## 需要決定的事

確認使用者最重要的任務，以及品牌、資訊完整度與操作簡單度的取捨。

# 平台選型：Webflow、Shopify、WordPress 或 Headless

依內容、交易與營運需求選平台，並把長期成本算進來。

## 這是什麼

平台選型是在內容管理、交易功能、擴充彈性與維護成本之間做取捨。最適合的平台取決於網站要完成的工作。

適用情境：新網站立項、舊平台限制工作，或考慮改成客製前台時。

## 為什麼重要

- 平台會決定內容效率、整合成本與後續維護負擔。
- 先驗證最難需求，能避免開發到一半才發現方案限制。

## 掌握重點

- **按主要用途比較平台**：內容行銷站可評估 Webflow；交易營運評估 Shopify；既有生態與外掛需求可評估 WordPress。
- **客製彈性伴隨維護責任**：多通路內容、複雜整合或權限可能需要 Headless／客製，但要承擔更多系統維運。
- **把長期成本一起比較**：比較內容模型、語言、SEO、整合、可攜性與總持有成本；依當前方案驗證能力。

## 舉個例子

- 情境：一個主要需要快速更新文章的網站，未必需要複雜客製系統。
- 重點：先列營運需求，才知道多一分彈性是否值得多一分維護。

## 從這一步開始

列出不可缺少的功能、誰維護，以及一年可負擔的成本。

## 開始前準備

- 編輯與交易流程、多市場和權限需求
- 既有資料、整合、主機、預算與維運能力

## 依序完成

1. 建立需求 × 平台矩陣，列出限制、依賴和退出方式。
2. 對付款、搜尋、預覽或整合等高風險需求做小型 PoC。
3. 輸出架構決策紀錄、成本假設及交接責任。

## 完成時檢查

- 推薦理由可追到需求；關鍵能力有現行文件或 PoC 證據。
- 費用列出日期、用量與方案假設，未核准不購買。

## 容易忽略的事

- 因為熟悉某工具而忽略營運需求。
- 認為 Headless 一定更快或一定比較便宜。

## 需要決定的事

比較初期費用、長期維護和營運彈性，再用小型驗證確認關鍵功能。

# 開發交付：功能、品質與可維護性

完成定義包含可用、可測、可交接，不是頁面能打開而已。

## 這是什麼

開發完成代表使用者能順利做完主要任務，也能在失敗時得到清楚回應，後續維護者有辦法接手。

適用情境：準備驗收網站、交接程式，或修正反覆出現的問題時。

## 為什麼重要

- 提早驗證主流程與整合，能降低上線後才發現錯誤的成本。
- 可重現建置與交接能避免只有原開發者修得動。

## 掌握重點

- **驗收看完整旅程**：驗收涵蓋主流程、錯誤狀態、權限、相容性、SEO 與效能。
- **速度要看實際使用情況**：Core Web Vitals 看實際使用者資料；實驗室分數用來診斷，不等於實際表現。
- **測試和正式環境要分開**：開發、staging、production 分離；機密不進前端、版本庫或測試紀錄。

## 舉個例子

- 情境：首頁正常，但付款失敗後畫面沒有任何提示。
- 重點：驗收要看完整流程與失敗情況，不能只看正常畫面。

## 從這一步開始

列出三個最重要的使用任務與各自的失敗情況。

## 開始前準備

## 依序完成

2. 執行適合變更風險的檢查，驗證資料、權限與主要使用路徑。
3. 檢查行動版、鍵盤、效能及索引條件，修復相關失敗。
4. 交付可建置版本、執行方式、測試證據與已知限制。

## 完成時檢查

- 乾淨環境可依文件建置，主流程有實際結果。
- 變更可審查、可回復；未執行的檢查明確列出。

## 容易忽略的事

- 只有綠色 build，沒有功能驗證。
- 把所有測試 mock 掉再宣稱整合成功。

## 需要決定的事

確認驗收標準與剩餘風險；會影響主要任務的問題要先修復。

# 上線量測：GA4、GSC、Google Ads 與 Meta

先釐清要量什麼，再接好流量、行為與成交資料。

## 這是什麼

量測是把網站行為轉成可判斷的資料。GA4、GSC 和廣告平台各看不同環節，合起來才能理解成效。

適用情境：網站上線、活動開始，或團隊需要回答「流量從哪來、為什麼沒有成交」時。

## 為什麼重要

- 沒有可靠量測，上線後無法判斷流量與活動是否帶來成果。
- 重複 purchase、幣別或 consent 錯誤會直接影響廣告優化和商業判讀。

## 四個工具，四種問題

 | 概念 | 說明 |
 | --- | --- |
 | GSC | 搜尋結果有沒有被看見、點進來？ |
 | GA4 | 進站後做了什麼、在哪裡離開？ |
 | Google Ads | Google 廣告帶來什麼成果？ |
 | Meta | Facebook／Instagram 廣告帶來什麼成果？ |

先決定想回答的問題，再選工具與事件。各平台的歸因方式不同。

## 掌握重點

- **不同工具回答不同問題**：GA4 看行為；GSC 看 Google 搜尋與索引；Google Ads／Meta 看投放與轉換，各自有不同歸因。
- **追蹤碼與 SEO 標籤各有用途**：SEO title／description、OG tags 與 Meta Pixel 是不同東西；GTM 是可選部署工具，不是全部追蹤。
- **事件名稱和成交定義要一致**：電商事件要定義觸發點、transaction_id、items、value、currency；個資不能隨意送進分析。

### 名詞小抄

- **GA4**：Google Analytics 4，觀察進站後的行為與轉換。
- **GSC**：Google Search Console，觀察 Google 搜尋曝光、點擊與索引。
- **GTM**：Google Tag Manager，用來管理追蹤標籤的工具。

## 舉個例子

- 情境：GSC 顯示搜尋點擊增加，GA4 卻顯示訪客在商品頁離開。
- 重點：前者回答能否被找到，後者幫忙定位進站後的問題。

## 從這一步開始

先列出最想回答的三個商業問題，再決定需要哪些事件。

## 開始前準備

- 既有 GA4／GSC／GTM／廣告帳號 ID 與授權連線
- 事件、成交定義、來源系統、測試訂單及市場隱私要求

## 依序完成

1. 先盤點現有原生 App、theme、GTM 和 server-side 實作，畫唯一事件責任表。
2. GA4／GSC 與 Google Ads／Meta 都列標準盤點；依渠道計畫接線，未使用者註明理由及未來需求，不直接略過。
3. 測試 consent 接受／拒絕、購買、退款與重複載入；Meta Pixel／CAPI 以相同 event_name／event_id 去重。
4. 比對 DebugView／平台測試事件與實際訂單，保留 payload、時間及去重證據；說明歸因差異。

## 完成時檢查

- 一筆測試訂單只有一筆有效成交，金額幣別與訂單一致。
- 同意與拒絕行為符合核准規則；報表不暴露個資。

## 容易忽略的事

- 只確認 tag 有載入，沒測事件。
- 重建既有 property，導致歷史資料斷開。

## 需要決定的事

確認哪些行為代表成果，以及資料收集與同意規則。

# 網站上線：一次看完必要條件

上線前一次確認 SEO、交易、追蹤、DNS 與回復方案。

## 這是什麼

網站上線是把通過驗收的版本切到正式環境，並確認使用者、搜尋引擎與營運流程都能正常接續。

適用情境：準備發布新站、改版切換，或需要決定能否正式上線時。

## 為什麼重要

- 上線是一次系統切換，漏一個環節就可能造成流量、交易或資料損失。
- 有明確 go／no-go 與回復條件，團隊才能快速決定。

## 掌握重點

- **上線要看整套系統**：至少涵蓋功能、內容、SEO、量測、隱私、DNS／TLS、效能、備份和責任交接。
- **既有搜尋與量測要接續**：GA4／GSC 先盤點沿用；Google Ads／Meta 依實際渠道啟用；title、description、OG tags 分開查。
- **正式環境需要再次驗證**：預覽站不是正式站；production 的索引、表單、付款與追蹤需再驗證。

## 舉個例子

- 情境：預覽站表單正常，上線後正式環境卻缺少接收設定。
- 重點：上線前測試，切換後還要在正式網址再驗證。

## 從這一步開始

把必要項目列成通過、未通過與待決定三種狀態。

## 開始前準備

- 核准版本、網域與上線窗口、決策及維運聯絡人
- 驗收、301、事件、DNS、備份與回復計畫

## 依序完成

1. 整理 go／no-go 表，先驗證 staging 主流程、SEO、量測及必要政策。
2. 盤點正式 DNS／TLS／郵件、資料同步、環境變數與監控，準備可回復版本。
3. 在既有上線授權內執行切換，依適用情境移除 production noindex／密碼保護。
4. 檢查代表 URL、訂單或表單、事件與 GSC；交付帶時間和版本的上線收據及觀察表。

## 完成時檢查

- 正式站主要任務成功；舊 URL 對應正確；分析事件去重。
- 沒有 staging 限制殘留；監控與責任人已交接；未通過項有明確決定。

## 容易忽略的事

- 全站解除保護，連後台和預覽內容一起公開。
- 只看首頁，沒測表單、購物或 redirect。

## 需要決定的事

依驗收結果決定是否上線，並確認誰能決定暫停或回復。
