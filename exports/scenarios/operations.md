# Hosting、DNS、CDN 與環境

釐清服務由誰代管，以及域名、應用、資料和郵件如何連在一起。

## 這是什麼

網站能被打開，仰賴域名、DNS、主機、內容與網路服務一起運作。知道各層的責任，才能選型、維護與排錯。

適用情境：規劃代管、更換網域，或遇到網站／郵件連線問題時。

## 為什麼重要

- 主機選擇影響可用性、費用、維護責任與事故回復。
- 知道域名、DNS 和郵件的關係，能避免搬站時一起弄壞公司信箱。

## 從輸入網址到打開網站

 | 概念 | 說明 |
 | --- | --- |
 | 域名與 DNS | 找到服務位置 |
 | CDN／網站主機 | 接收與處理請求 |
 | 應用與內容 | 產生可讀的頁面 |

簡化的請求路徑；實際平台可能合併多層。郵件服務另有 DNS 紀錄。

## 掌握重點

- **代管範圍依平台與合約決定**：Shopify／Webflow 平台代管與 VPS／雲端自管的責任不同；由實際合約界定。
- **先分清系統層次**：域名註冊、DNS、CDN、TLS、應用與資料庫分層管理，不把所有問題當主機問題。
- **環境、備份與回復一起規劃**：定義 dev／staging／prod、資料區域、RTO／RPO、備份與監控；流量和費用估算註明假設。

### 名詞小抄

- **DNS**：把域名連到網站、郵件等服務的查詢紀錄。
- **CDN**：把內容放在不同地區節點，加快傳送的服務。
- **TLS**：瀏覽器與網站之間的加密連線機制。

## 舉個例子

- 情境：搬網站時改了 DNS，卻一起覆蓋郵件紀錄，造成信件收不到。
- 重點：網站和郵件共用域名，但各自的紀錄與責任需要分開確認。

## 從這一步開始

先畫出域名、DNS、網站、資料和郵件分別由誰管理。

## 開始前準備

- 應用架構、流量與資料類型、目前 DNS 區域
- 帳號擁有人、預算、SLA、備份與復原需求

## 依序完成

1. 整理架構、DNS 與第三方依賴，標明平台／Tenten／客戶責任。
2. 比較代管與自管、成本和擴充方式；盤點 CDN、TLS 和資料持久化。
3. 產出環境配置、備份／回復、監控和存取交接方案。

## 完成時檢查

- 正式域名與 TLS 正常，MX／TXT 等郵件紀錄保留。
- 重啟／重建不遺失持久資料，備份有隔離回復證據。

## 容易忽略的事

- 把 DNS TTL 當保證立即切換。
- 只備份程式，沒有資料庫和媒體。

## 需要決定的事

確認預算、可用性與資料存放條件，並指定每一層的維護責任。

# 維運、安全與事故回復

監控看得到問題，備份真的能還原，事故有人做決策。

## 這是什麼

維運讓服務持續可用；事故準備則讓問題發生時，團隊知道如何發現、處理與恢復，並減少資料損失。

適用情境：接手網站代管、規劃備份，或需要讓事故處理不再依賴某一個人時。

## 為什麼重要

- 備份存在不代表能回復；事故時需要可操作的流程和證據。
- 最小權限與環境隔離可降低錯誤或外洩的影響範圍。

## 掌握重點

- **先定能承受的中斷與資料損失**：RTO 是可接受回復時間，RPO 是可接受資料損失窗口；由商業需求決定。
- **權限需要持續整理**：帳號和機密走安全連線；離職、供應商與 Agent 權限需撤銷和定期盤點。
- **監控與更新要能發現問題**：監控至少看可用性、關鍵任務、錯誤與備份；更新先檢相容性並保留回復方式。

### 名詞小抄

- **RTO**：可接受的服務回復時間。
- **RPO**：可接受的資料損失時間範圍。

## 舉個例子

- 情境：每天都有備份，真正故障時卻發現資料無法還原。
- 重點：備份存在和可以恢復服務是兩回事，還原要實際演練。

## 從這一步開始

先決定服務能中斷多久、可接受多少資料損失，再檢查備份。

## 開始前準備

- 系統及權限清單、備份位置、回復需求
- 事件負責人、聯絡路徑、變更窗口與合約責任

## 依序完成

1. 驗證最小權限、資料保存與更新流程，記錄可修正風險。
2. 在隔離環境做還原演練，量測時間與資料缺口。
3. 建立有閾值、通知與升級人的監控；測試告警是否真的送達。
4. 事故先穩定服務和保留證據，記錄時間線、影響、修復及後續行動。

## 完成時檢查

- 有實際 restore 結果；告警能到正確值班角色。
- 事故與變更有版本、責任人及可追溯紀錄，不在收據洩露機密。

## 容易忽略的事

- 承諾未簽訂的 24／7 或回應 SLA。
- 用刪除記錄掩蓋故障，或未對帳就回復舊資料。

## 需要決定的事

確認事故由誰決策、如何溝通，以及服務中斷與資料損失的可接受範圍。

# API、MCP 與跨系統自動化

讓系統可靠交換資料，重跑不重複，失敗能追查。

## 這是什麼

跨系統自動化讓資料在工具之間可靠流動。API 是系統提供的操作介面；MCP 讓 Agent 以一致方式使用工具。

適用情境：需要把表單送到 CRM、訂單接到物流，或讓多個工具共用資料時。

## 為什麼重要

- 整合的價值在工作持續正確流動，不只是 API 回傳 200。
- 資料責任與去重規則能避免多份名單、重複訂單或意外寄送。

## 掌握重點

- **資料要有明確來源**：每個欄位指定唯一資料來源，說明同步方向、識別鍵與衝突規則。
- **同步會失敗，也可能重複**：webhook 可能重送、延遲或亂序；驗簽、去重、限流及重試要依平台契約設計。
- **權限和資料可信度分開處理**：外部內容視為不可信資料；工具權限在系統層約束，機密不交給模型自由輸出。

## 舉個例子

- 情境：表單重送兩次，CRM 就建立了兩筆相同商機。
- 重點：同一動作要能被辨認，重試才能補救失敗而不製造重複。

## 從這一步開始

列出資料從哪裡來、要到哪裡去，以及辨認同一筆資料的方式。

## 開始前準備

- 來源和目的系統、API／MCP／CLI 能力與安全連線
- 範例 payload、資料映射、觸發與例外規則

## 依序完成

1. 盤點現有整合，確認 schema、認證、版本、限額和 sandbox。
2. 建欄位映射與 idempotency key，加入驗證、退避重試、失敗佇列與對帳。
3. 測試重送、亂序、部分成功、權限不足與注入內容，隔離真實客戶。
4. 交付流程定義、觀測紀錄、重跑與回復方式；不支援的能力具體回報。

## 完成時檢查

- 同一事件重送不造成重複副作用，最終資料可對帳。
- 失敗有告警與人工負責人，log 不含機密或不必要個資。

## 容易忽略的事

- 對所有錯誤無限重試，造成重複扣款或寄信。
- 兩個系統同時寫入同一欄位，卻沒有衝突規則。

## 需要決定的事

確認資料由誰負責，以及哪些外部動作可以自動執行。
