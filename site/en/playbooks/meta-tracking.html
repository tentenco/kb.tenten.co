Meta Pixel, CAPI and deduplication

Report real purchases without counting browser and server copies twice.

Understand the conceptMain pointsTake actionCheck the result

Start here

What is it?

Meta tracking reports purchases to Facebook and Instagram advertising. Pixel sends from the browser; CAPI sends from the server.

When to use it

Use this before Meta campaigns or when purchase totals look wrong.

Why it matters

  • Valid purchase events support ad learning and evaluation.
  • Browser and server tracking complement each other, but duplicate purchases inflate ROAS.

What to know

Remember these 5 points

  1. Understand both senders

    Pixel sends browser events; CAPI sends server events. Neither is an SEO meta or Open Graph tag.

  2. Connect shopping actions

    The core path includes ViewContent, AddToCart, InitiateCheckout and Purchase. Keep value, currency and product IDs consistent.

  3. Match event identity

    For the same event, match event_name and use the browser eventID as the server event_id. Reuse a stable ID for that action.

  4. Check custom storefronts

    Shopify’s official Meta channel covers some events. Verify custom headless storefront coverage separately.

  5. Respect consent

    CAPI still requires appropriate consent. Sharing levels, customer data and purposes must follow approved rules.

Glossary 3 terms
Pixel
Browser code that records and sends events.
CAPI
Conversions API for sending server events.
Deduplication
Recognizing multiple reports of one action.

In practice

An example

Pixel and CAPI report one purchase without a shared identifier.

What to take from this

Match the reports to prevent counting it twice.

Put it to work

Start here

Inventory Pixel, CAPI and official integrations; identify each sender.

Before you start 2 items
  • Existing business/ad accounts, Pixel/dataset, catalog and access
  • Event ownership, product ID mappings, consent rules and test orders
  1. Inspect official channels, GTM, code and server senders. Assign clear event ownership.
  2. Configure supported APIs/native integrations within authorization. Match content_ids to the catalog.
  3. Use Test Events and diagnostics for purchases, rejected consent, reloads and retries. Inspect browser/server pairing.
  4. Deliver de-identified payloads, timestamps, matched IDs and order-value reconciliation; list uncovered paths.

How to check the result

  • ✓One test purchase becomes one valid conversion, with evidence of browser/server pairing.
  • ✓Rejected sharing follows approved rules; events reveal no extra customer data.

Decisions to make

Agree on data sharing and channel use. Tracking setup and ad activation are separate decisions.

Common pitfalls

  • Duplicating sends from the official app and manual Pixel.
  • Generating a new event_id on each retry or relying only on Pixel Helper.
Sources and scope

Reviewed 2026-10-21 · Suggested guidance; adapt to the project

  • Shopify: Meta data sharing ↗Pixel/CAPI, sharing levels, standard events and data use. Custom storefront coverage needs separate tests.
  • Meta: deduplicate Pixel and CAPI events ↗Matching event names and eventID/event_id for deduplication. No customer account was verified.
  • Shopify: customer privacy settings ↗Privacy settings, consent, opt-outs and data purposes. Does not provide a legal determination.
