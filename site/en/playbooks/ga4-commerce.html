GA4 ecommerce events and conversion rates

Connect product views, carts, checkouts and purchases into a funnel you can reconcile.

Understand the conceptMain pointsTake actionCheck the result

Start here

What is it?

GA4 records customer actions as events. Connecting views, carts, checkouts and purchases reveals the shopping funnel.

When to use it

Use this to inspect drop-offs, calculate conversion rates or verify purchase tracking.

Why it matters

  • Funnel losses show whether to improve the product page, cart or checkout.
  • Inconsistent denominators, amounts and events lead to conflicting conclusions.

What to know

Remember these 5 points

  1. Record shopping actions

    Core events include view_item_list/select_item, view_item, add_to_cart, begin_checkout, purchase and refund. Add shipping and payment events as needed.

  2. Include reconciliation fields

    Define triggers, item_id, items, value and currency. Use a stable transaction_id to match purchases and refunds to orders.

  3. Define the denominator

    Purchase session conversion rate is sessions with a purchase divided by all sessions in the same scope. Orders per session and all-key-event rate differ.

  4. Compare the same scope

    If 100 of 10,000 sessions include a purchase, the rate is 1%. Align time zone, device, market, period and consent coverage.

  5. Account for platform differences

    GA4, Shopify and Ads have different attribution and tracking limits. Order accounting is the transaction baseline; reports need not match exactly.

Glossary 3 terms
Event
A recorded action, such as adding to cart.
Session
A group of interactions during one visit; a user can have several.
transaction_id
An order identifier used to recognize the same transaction.

In practice

An example

If 100 of 10,000 sessions contain a purchase, purchase session conversion is 1%.

What to take from this

State the denominator before comparing rates.

Put it to work

Start here

Agree on what counts as a purchase and conversion before checking events.

Before you start 2 items
  • Property, data stream, event sources and test environment
  • Product/variant ID mappings, tax and shipping value rules, de-identified test orders
  1. Define one sender per event and parameter. Check native integrations and gaps between custom storefront and hosted checkout.
  2. Verify cross-domain source continuity; avoid self or payment-provider referrals. Do not send personal data such as email to analytics.
  3. Check event order, values and currencies in DebugView, requests and reports. Test reloads, failed payments, refunds and consent.
  4. Deliver a funnel and metric dictionary with numerators, denominators, test exclusions and reasons for discrepancies.

How to check the result

  • ✓Reloads do not duplicate purchases; refunds match the original transaction.
  • ✓Reports show funnels by channel/device and reproduce the agreed conversion rate.

Decisions to make

Agree on purchase, revenue and conversion definitions.

Common pitfalls

  • Sending purchase on a checkout-button click or failed payment.
  • Calling orders divided by users a session conversion rate.
Sources and scope

Reviewed 2026-10-21 · Suggested guidance; adapt to the project

  • Google Analytics: ecommerce events ↗Ecommerce events, items, currency, transaction_id, purchases and refunds. Check current Meta/Ads documents when implementing those platforms.
  • Shopify: Web Pixels API ↗App/custom pixel sandboxes, customer events and privacy APIs. Does not guarantee automatic coverage of Astro storefronts.
  • XTERRA code and integration snapshot ↗Astro/Sanity/Shopify boundaries, custom forms, Klaviyo adapter/Draft scripts, Judge.me and development launch restrictions. Does not establish live configuration, sending or production availability.
