# 電商售後：通知、客服、退貨與保固

訂單成立後仍是顧客旅程，把交付與後續服務一起接通。

## 這是什麼

售後服務連接訂單、出貨、客服、退貨與保固。顧客送出需求後，要能知道進度，也要有明確的人或流程接手。

適用情境：規劃電商上線、客服表單，或處理反覆發生的配送與退貨問題時。

## 為什麼重要

- 找不到訂單、配送或保固資訊，會增加客服成本與退款。
- 表單有成功畫面不代表案件已送達、有人處理或顧客已收到回覆。

## 掌握重點

- **各系統的責任要清楚**：Shopify 管訂單／履約基準；物流、ERP／3PL、客服工單和行銷平台的責任需分開。
- **通知避免漏寄或重寄**：訂單確認、出貨、取消／退款與服務回覆是不同通知；避免多個系統重寄。
- **大型商品有額外配送條件**：大型器材加驗偏遠配送、樓層／搬運、組裝、破損回報與退運成本，規則由商家確認。
- **服務資料與行銷同意分開**：保固／產品註冊需型號、序號與購買資料；服務同意不自動變成行銷訂閱。
- **工具依服務量與流程選擇**：先用原生通知／流程；工單、退貨入口等工具有量或流程需求才加，headless 查 API 支援。

### 名詞小抄

- **ERP**：整合企業營運資料的系統，例如庫存與財務。
- **3PL**：第三方物流服務商。

## 舉個例子

- 情境：顧客送出保固申請，網站顯示成功，客服卻沒有收到。
- 重點：資料被保存和案件被處理是兩件事，兩段都要驗證。

## 從這一步開始

挑一種常見售後需求，畫出提交、收件、處理與回覆流程。

## 開始前準備

- 核准的運送／退換貨／保固政策、物流及服務責任人
- 現有訂單／表單／工單／通知資料流與內部測試收件人

## 依序完成

1. 畫訂單到出貨、異常、退貨／退款的狀態與通知責任，定義唯一案件／訂單鍵。
2. 以代表地址／商品驗證運費、不可配送、退款與庫存回補；財務、物流狀態各自對帳。
3. 接好詢問／註冊／保固表單的保存、派送、重試及告警，保護附件和個資。
4. 測試正常、重送、服務商失敗與無行銷同意案例；交付通知收件／工單與重試證據。

## 完成時檢查

- 每筆測試案件可查收據、處理狀態和責任；失敗可追蹤，不無聲遺失。
- 訂單與退款金額／庫存一致；通知不重複且未誤訂閱行銷。

## 容易忽略的事

- 把收到 API 202 或表單寫入成功當成已送信。
- 以為 CRM 建好 Profile 就完成客服派單或保固服務。

## 需要決定的事

由商家確認退貨、保固、費用和服務承諾，再把規則落實到流程。
